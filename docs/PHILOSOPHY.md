# 构方：把软件的配方交给 Agent

> 别写软件了，写提示词吧，未来的人工智能会完整重建它！

这是 Recipkg 的愿景。当前的工具负责保存、整理和交付重建材料；它不保证任意提示词都足够完整，也不保证任意模型都能成功重建软件。

## 本质是什么

一份软件配方回答四个问题：软件要做什么、它依赖什么、组件怎样配合、怎样判断结果正确。Agent 根据这些材料生成实现。Recipkg 管理这些材料及其版本，不替 Agent 编写或执行软件。

我们希望长期维护的是可以复用和审阅的意图、接口与验收条件。实现代码可以是某次构建的产物；当环境、语言或工具变化时，同一份行为约定仍然有价值。

## 从机器码、汇编到源代码，再到提示词

可以把这条线理解为一种表达愿景：人们希望越来越直接地表达自己要的行为，把更多机械转换交给工具。机器码描述处理器执行的指令；汇编给指令取了可读名字；更高层的源代码表达算法与结构；软件配方进一步记录目标、约束和验收方法。

这不是严格的软件历史分期，也不是所有软件都会走向同一种开发方式。不同层次长期并存。自然语言中的歧义、模型能力、环境差异和不完整的验收条件，都是重建过程中必须处理的实际问题。

## 为什么要递归依赖

如果根提示词写着“使用某个组件”，却没有给出组件的行为说明，那么重建依赖了包外的知识。Recipkg 因此把每个配方的依赖继续展开，直到所需配方都已包含。

一个完整归档包含根配方、每层依赖的原文、来源记录和文件校验值。重复出现的依赖按各自别名保持独立作用域；缺失节点、循环或校验失败都必须明确报错。

提示词材料齐全仍然不等于整个运行环境都被包含。例如操作系统、编译器、第三方账号、远程服务或数据集可能需要额外准备。这些前提必须写清楚，不能把一个外部服务的链接说成已完成的软件重建。

## 0 代码的范围

配方归档只保存 UTF-8 Markdown 文件。配置是 `RECIPE.md` 中的 TOML 块；技能保留标准 `SKILL.md` 文件头；验收条件可以写成文字、表格和输入输出样例。

归档不携带实现源文件、二进制、文件系统链接或安装钩子。Markdown 中允许解释接口、给出声明式配置和示例，但不应把完整实现改名为 `.md` 来绕开这个约定。CLI 的文件检查不能证明任意自然语言内容都符合这一语义要求。

包管理器本身当然由代码实现，Agent 最终生成的软件也可以包含代码。包格式独立于工具的实现语言、模型厂商和生成软件的语言。

## 怎样才算重建成功

重建成功首先意味着：在说明的环境和输入范围内，生成的软件满足事先定义的可观察行为。它不要求与旧软件使用同样的内部结构，也不承诺源码或二进制逐字节相同。

验收条件必须在实现之前明确。通过一些测试只能说明被这些测试覆盖的行为符合约定；不能据此宣称所有未描述行为都已经恢复。行为缺口、推断和未运行的检查都应保留在报告中。

## 小工具的边界

五个主要动作生成标准化提示词：软件到提示词、提示词到软件、重写软件、添加依赖、发现依赖。它们不调用模型，也不执行生成的软件。用户把提示词交给自己选择的 Agent，继续完成对应工作。

包操作负责解析、检查、打包、安装、校验和同步技能。输入清楚时应产生清楚的结果；无法完成时应给出明确错误。这个边界让同一份配方可以交给不同 Agent，也便于独立检查重建材料。
