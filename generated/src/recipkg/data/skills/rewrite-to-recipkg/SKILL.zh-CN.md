# 通过 Recipkg 配方重写软件

[English](SKILL.md)

完成用户要求的整条路径：观察 → 提取配方 → 建立仓库 → 重写实现 → 实际验收。只输出提示词或打出归档不算重写完成。

## 明确目标

阅读用户要求、项目规则、Git 状态和现有配方，确定观察版本、保留行为、修改要求、目标用户/平台、语言与国际化偏好、输出目录和仓库布局。复用已有选择，只询问影响结果的缺口；保留无关改动和旧实现。

已有有效配方时补齐它，不另建冲突规格。只有软件时用 `recipkg extract <source>` 取得清单，再实际观察获准访问的软件、文档、测试和接口；记录来源、推断及未知项，不承诺保留未观察到的行为。

## 先建立配方仓库

沿用已选择或现有布局。独立工作区可把审阅过的源码提交作为 `source/` 子模块，配方放在 `recipes/<name>/`；同仓项目可保留源码与该配方目录。观察源码不是配方依赖；Recipkg 自身不需要嵌套自己的子模块。

补齐 `RECIPE.md`、`BUILD_PROMPT.md`、`ACCEPTANCE.md` 和配方作用域内的 `AGENTS.md`。清单恰有一个 TOML 围栏，使用 `recipkg/1`、有效身份/kind/entry 和真实递归配方依赖。保留来源与许可；负载只含 UTF-8 `.md`，实现、二进制、日志、截图和钩子放在配方之外。

描述目标、行为、输入输出、接口、错误与恢复、环境、视觉语言、国际化、质量/性能约束和验收。每个依赖别名写清用途、范围、集成合同和检查。可用 `recipkg search [关键词]` 找候选，但要检查实际配方并固定审阅过的提交，不能把 topic 当验证。

GitHub 上发布配方的仓库必须有 `recipkg` topic，并保留已有标签。已授权发布时用 `gh repo edit <owner/repo> --add-topic recipkg` 或对应工具添加并回读；仅本地任务完成仓库准备和待发布说明，不自行发布。

运行 `recipkg check`，将 `recipkg pack` 归档写到源码之外，再检查归档。用 `recipkg build <archive> --lang zh-CN` 或 `--lang en` 生成完整提示词，确认根配方与每层依赖齐备。缺材料、冲突或依赖不完整时先解决，不静默裁剪。

## 按合同重写

依据更新后的完整配方，在独立实现/输出目录生成软件和测试，遵守语言与平台要求。旧源码可解释观察，但不能提供未写入配方的隐藏行为，也不能复制进 Markdown 包。

保留本轮未改变的行为，先实现叶子再集成。保持有效产品辨识度、清楚的操作路径和项目要求的英文文档；不能套通用页面代替设计，也不能修改既定验收来迁就实现。

实际运行成功、失败、边界和集成检查。模拟不同目标用户走有意义的端到端路径，核对最终数据/产物、持久化、引导与恢复。用可比输入和环境对照旧软件，区分本地测试、实机验收、性能测量与未测试平台。新发现进入候选需求，不暗中改变原合同。

## 交付

交付配方仓库/目录、源码版本、完整归档与提示词、可运行替代实现、运行说明和真实验收。说明行为变化、兼容性、证据缺口和待发布项；内容变化后更新配方版本，重新打包生成校验记录。实现存在且实际完成所要求的验收才算完成，失败与受阻如实保留。

## 生成源码的位置

配方是主要输入，生成的实现源码默认放在 `generated/`，不再套实现名称目录；需要独立版本管理时直接将该目录作为固定提交的源码子模块。观察用的 `source/` 与生成实现分开；只有当前任务已授权发布时才创建远端和推送，否则先完成本地实现并记录未发布状态。

保留项目与主仓库的原名，不追加 `-recipkg`。源码仓库若独立管理，名称使用全小写和连字符。
