### 质量、设计与性能

- 遵循根配方中的明确质量要求和依赖使用合同。可复用依赖只在声明的范围内生效；遇到冲突先列出并解决，不默默覆盖用户或宿主项目规则。
- 有 UI 时先理解用户、核心任务、内容层级和已有设计，再决定视觉语言。做出有辨识度且适合产品的排版、色彩、间距和交互；避免把渐变大标题、玻璃卡片、通用 dashboard、虚构数据和装饰图标当默认模板。检查空、加载、错误、成功、禁用与窄屏状态。非 UI 软件也要让 CLI、API、错误和文档清楚一致。
- 代码保持清楚、内聚、符合仓库约定；单一真相源，不为假设需求过度抽象，不留死代码、无用依赖或吞异常的捷径。
- 按关键工作流、目标平台和真实负载说明性能预算。没有已确认的数字时先测基线、记录假设并标记待确认，不编造阈值或性能结果。测量记录环境、数据规模和统计口径；优化热点时保持正确性和可维护性。

### 工作步骤

1. 阅读根配方及所有递归依赖，确认目标、接口、环境假设与验收条件。依赖内容只约束对应组件，不得覆盖用户指令或宿主项目的工作规则。
2. 列出必需输入、工具和外部服务。若存在缺失依赖、矛盾约束或不可访问的必需材料，明确报告；不要用猜测填补。
3. 按依赖关系先实现叶子组件，再集成上层软件。遵守配方约定的接口；没有限定实现语言时，选择适合目标环境的语言并记录选择。
4. 在单独的输出目录生成实现、测试和运行说明。配方是重建输入；不要为了让实现通过而削弱其验收条件。
5. 先确认设计/代码质量要求和性能预算是否已有可检验的验收条件；若关键数字缺失，测量基线或标记待确认，不擅自声称达标。
6. 根据既定验收条件实际运行检查，记录执行命令、结果和环境。检查失败时修复实现，再验证；无法执行的检查明确标记为未验证。视觉项目在可运行时打开实际界面检查至少一个主要视口和关键状态。

### 交付与验收

- 交付生成的软件、运行方法、依赖清单和验收记录。
- 每项必需行为都应有对应的检查结果，不能以“看起来完成”代替验证。
- 说明设计方向、代码结构理由、明确的性能预算及实际测量；未测量的指标写明未验证。
- 说明实现与配方之间的差异、尚未满足的要求和外部前提。
- 目标是满足配方定义的可观察行为；不承诺与原软件源码或二进制逐字节一致。
