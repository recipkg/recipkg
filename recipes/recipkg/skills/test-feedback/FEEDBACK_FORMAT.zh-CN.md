# 测试反馈与需求交付格式

[English](FEEDBACK_FORMAT.md)

按项目现有文档约定组织；小任务可合成一份 Markdown。以下字段用于保留从事实到需求的过程，不要求填写无依据的数字或制造问题来凑条数。

## 本轮范围与证据

- 软件/配方版本、环境、日期、实际运行入口与测试范围。
- 角色、目标与约束；说明哪些来自配方，哪些是本轮假设。
- 对每条任务记录：起点 → 操作 → 最终结果验证；预期、实际、通过/失败/受阻、证据位置。
- issue 检索的项目、选择理由、查询范围/时间与访问限制；无匹配结果也如实记录。
- 证据编号指向复现步骤、截图/日志路径或 issue 永久链接；不要记录密钥和无关个人信息。

## 候选需求

| 字段 | 内容 |
| --- | --- |
| 编号与标题 | 稳定编号及要解决的用户问题 |
| 类型 | 缺陷 / 可用性 / 新需求 / 审美偏好 / 待验证假设 |
| 角色与场景 | 谁在什么条件下想完成什么任务 |
| 当前障碍 | 配方承诺或用户预期，与实际结果的差别 |
| 证据与状态 | 本地实测 / 本项目 issue 报告 / 相关项目 issue 报告 / 推断；注明版本、链接和本地是否已复现 |
| 影响与优先级 | 影响核心任务、数据或恢复的方式；给出排序理由和已有替代方法，不编造普遍性 |
| 建议行为与边界 | 最小可观察变化、应保留的行为；可选方案及尚未决定的部分 |
| 验收 | 给定前置条件和输入，执行具体操作，应观察到什么；必要的失败/恢复与回归场景 |
| 下一步 | 可进入配方 / 需进一步验证 / 暂缓；说明仍缺什么证据或决定 |

外部报告只能证明有人报告过相应问题，不能证明本项目当前版本有该缺陷。Agent 模拟用户只能提供走查线索，不能给出真人满意度或用户覆盖率。

## 不混淆的两种示例

以下是格式示例，不是对某个真实项目的测试结果：

- **已复现的可用性问题**：首次使用者在错误状态只看到代码，无法得知允许的有限选项。证据需包含实际入口、输入和返回内容。候选行为是列出允许值并给出一个可执行示例；验收应同时覆盖合法输入成功和非法输入后可修正，不只检查提示文字是否存在。
- **待验证的外部线索**：相关项目有人报告低网速下重复提交。先记录原 issue 的版本、讨论结论和与本项目的联系；本地未测时不得标为已复现。下一步是用可控网络条件验证本项目的结果数量、状态反馈和重试行为，再决定是否生成修改合同。

## 交付时说明

概述实际完成的任务、主要发现和优先需求，保留反例、未复现、无问题与受阻的结果。列出未测试的平台/角色、外部来源限制，以及需求是否已经进入配方或仅是建议。一次测试没有发现问题，不等于所有使用方式都正确。
