## 任务：软件到提示词

把下列软件提炼为可以独立交给另一个 Agent 的软件配方。

### 工作步骤

1. 阅读可获得的源码、文档、界面和测试，记录本次观察的版本或提交。区分已经验证的行为、推断和未知项；无法访问的内容不要补写成事实。
2. 描述用户目标、输入输出、公开接口、数据格式、状态变化、错误处理、边界条件和运行环境。保存重要的行为与约束，不要求复刻内部实现。
3. 有视觉界面时记录实际观察到的视觉语言、层级、排版、密度、色彩角色、交互反馈、空/错/加载状态、窄屏和无障碍行为。区分观察、推断与未知，不把套用通用 AI 页面模式当成设计事实。非 UI 软件也记录 CLI 输出、错误信息、API 命名和文档的可读性。
4. 识别性能关键路径和约束：目标设备、代表性数据规模、启动或操作延迟、吞吐、内存、网络、包体积等。尽可能记录真实基线及测量环境；没有依据的目标数字标为待确认，不伪造性能承诺。
5. 识别直接依赖。区分需要重建的配方依赖、可复用的设计/工程质量合同、仅供参考的上游资料和实际运行所需的外部工具或服务。依赖声明必须指向具体配方；原始源码或普通提示词仓库先提炼为配方。
6. 编写 `RECIPE.md` 和 `BUILD_PROMPT.md`。`RECIPE.md` 使用唯一的 fenced `toml` 配置块；其余说明使用 Markdown。按需要补充 `ACCEPTANCE.md`、`DESIGN.md`、性能基线说明和 `AGENTS.md`。根构建提示词要明确列出每个依赖别名的职责、使用范围和集成验收，不能只声明别名。
7. 对重建所需的每个配方依赖重复上述提炼，直到叶子依赖完整。遇到缺失资料、循环依赖或无法重建的服务，明确列出阻塞原因。
8. 写出可观察的验收条件，覆盖行为、设计质量、失败路径、边界输入和有依据的性能目标；保留来源和许可说明。

### 最小配方格式

创建 `RECIPE.md` 与 `BUILD_PROMPT.md`。将下面唯一的 TOML 配置块放入 `RECIPE.md`，替换示例名称与描述；`BUILD_PROMPT.md` 保存完整重建说明。

```toml
format = "recipkg/1"

[package]
name = "example-software"
version = "0.1.0"
kind = "software"
description = "说明软件用途和主要行为"
entry = "BUILD_PROMPT.md"
```

包名仅用小写字母、数字和短横线，最长 64 字符；版本使用语义化版本。技能包使用 `kind = "skill"`、`entry = "SKILL.md"`，并保留标准 SKILL.md 的 YAML `name`、`description` 文件头。工具环境可用时，可先运行 `recipkg init <directory> --name <name> --kind software` 创建骨架。

本地配方依赖声明示例：

```toml
[dependencies.helper]
source = "../helper"
```

将依赖表放在同一 TOML 块内，不要为每个依赖新建配置块。

### 交付与验收

- 交付可阅读的软件配方及递归依赖；所有包文件必须是 UTF-8 `.md`。
- 不把实现源码、二进制、链接或执行钩子藏进配方。必要的接口约定和测试样例可以用 Markdown 表达。
- 未完成的依赖和不确定行为必须显式列出，不能声称配方已经完整。
- 配方应让未读过原始软件的 Agent 理解“做什么、依赖什么、怎样判断做对了”。
- 只报告实际观察到的设计与性能证据；无基线或无法实际打开界面的项目明确写出未验证项。

### 仓库约定

GitHub 上发布 Recipkg 配方的仓库必须有 `recipkg` topic。生成源码放在独立仓库，以固定提交的 Git 子模块接入 `generated/<源码仓库名>/`；`generated/` 只作容器，源码不进入配方负载。共享项目技能也复用相同上游仓库的子模块，不复制技能正文。发现配方候选可用 `recipkg search [关键词]`；标签和搜索结果都不代替有效配方与完整性检查。
