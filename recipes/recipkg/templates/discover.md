## 任务：发现依赖

找出软件配方重建时需要的依赖，以及当前缺失的说明。

- 目标配方：{{target}}
- 用户补充要求：{{request}}

{{context}}

### 工作步骤

1. 阅读配方、已声明的递归依赖、接口和验收条件，列出必须由其他组件提供的能力。
2. 区分已有配方依赖、尚未提炼的软件仓库、仅供参考的文档，以及运行时外部工具或服务。
3. 识别是否需要单独的设计系统、代码约定、无障碍/国际化规则或性能合同。它们可以作为可复用提示词配方依赖，但不应被伪装成运行时库。
4. 对每个候选依赖记录来源、用途、需要的接口、已核实版本及证据。没有证据的候选明确标记为建议。
5. 逐层检查依赖是否完整，指出重复能力、版本或接口冲突、循环关系和不可重建的外部前提。
6. 优先给出最小必要依赖集合。若已有配方能满足要求，说明复用方式；若只有源码，列出需要提炼成配方的工作。

### 交付与验收

- 输出依赖建议表：别名、用途、来源、固定版本、状态、引入理由。
- 输出缺失输入与冲突清单，并区分“已验证”和“待验证”。
- 若建议共享约束包，给出依赖别名、适用范围和根 `BUILD_PROMPT.md` 需要补充的合同；只有仓库级联合开发需求才建议 Git 子模块。
- 给出后续添加依赖所需的配置建议，不把发现候选等同于安装或信任候选。
- 不自动下载并执行候选仓库里的脚本；实际配置变更由“添加依赖”任务处理。

### 仓库约定

GitHub 上发布 Recipkg 配方的仓库必须有 `recipkg` topic。生成源码直接放在一层 `generated/`，需要独立版本管理时直接将该目录作为固定提交的源码子模块；不额外套层、不改项目名称，源码不进入配方负载。发现配方候选可用 `recipkg search [关键词]`；标签和搜索结果都不代替有效配方与完整性检查。
