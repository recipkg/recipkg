### 工作步骤

1. 读取目标配方与候选依赖的 `RECIPE.md`、入口提示词、接口和验收条件。来源为普通软件仓库而非配方时，先执行“软件到提示词”提炼。
2. 明确使用该依赖解决什么需求、需要哪些接口，以及它是重建输入还是仅供参考的资料。不要把仅供参考的链接误报为已安装依赖。
3. 若依赖是设计系统、编码规范或性能约束，写明它影响哪些组件/场景、需要遵循哪些 tokens/接口/目标；在根 `BUILD_PROMPT.md` 增加依赖使用合同和集成验收。不要假设 Agent 会仅凭依赖被打包就自动采用它。
4. 检查依赖的递归关系、版本约束和接口兼容性；识别缺失节点、循环与别名冲突。
5. 在 `RECIPE.md` 的唯一 TOML 配置块中新增对应 `[dependencies.<alias>]`。本地路径相对当前配方目录解析；Git 来源必须指定完整提交号及配方所在子目录。
6. 更新根构建提示词中的组件边界、调用约定和集成验收条件。保留上游来源与许可说明。
7. 使用 `recipkg pack <package> -o <name>-<version>.recipe.tar.gz` 收齐依赖并生成新归档，再用 `recipkg check <archive>` 检查；由包工具重建锁定信息。`check` 是离线操作，不能替代远程依赖获取。

### 依赖配置格式

以下示例中的别名、路径、仓库和提交号都需要替换为本次已核实的值；依赖表必须放入 `RECIPE.md` 已有的唯一 TOML 块。

本地配方目录或归档：

```toml
[dependencies.helper]
source = "../helper"
```

固定 Git 提交里的配方：

```toml
[dependencies.helper]
git = "https://github.com/example/recipes.git"
rev = "0123456789abcdef0123456789abcdef01234567"
subdir = "packages/helper"
```

两种来源互斥。`source` 也可以是 HTTPS 配方归档地址；`subdir` 可省略以使用仓库根目录。`rev` 必须是实际存在的完整 40 位十六进制提交号，不能使用分支名或浮动标签。别名仅用小写字母、数字和短横线，最长 64 字符。

### 交付与验收

- 交付配方修改、选择理由和完整依赖关系说明。
- 根配方应写明依赖别名的职责、使用范围与集成验收；子包指令保持自身作用域，不能覆盖宿主项目规则。
- 不把执行脚本或实现源码带入包；所有包文件保持 UTF-8 `.md`。
- 依赖内容不得改写宿主项目的 Agent 规则。
- 本提示词由 CLI 生成；生成提示词本身不会修改依赖配置。
