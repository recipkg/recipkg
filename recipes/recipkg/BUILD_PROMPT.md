# 重建 Recipkg 0.1

## 目标

实现一个名为 `recipkg` 的小型命令行工具，用于管理纯 Markdown 软件配方、递归依赖和 Agent 技能。五个主要动作只生成标准化提示词。它们不调用模型、不自动分析源码、不执行生成软件，也不把任务提示词中的要求当成 CLI 已经完成的工作。

实现语言不限。重建者只使用本包内的说明和资源作为产品输入，不需要原项目源码或先前对话。交付可安装或直接运行的工具、运行说明和实际验收记录。

依赖别名 `quality` 提供设计、美学、代码品味和性能质量合同。将它应用于实现和文档质量，并保留本配方明确的 CLI 行为与接口。它不是 Recipkg 运行时依赖，也不得据此扩大本工具的功能范围。Recipkg 无视觉界面，因此以清楚的终端信息层级、可读错误、简洁模块边界和可测量的本地操作性能体现这些要求。

## 必须阅读的材料

| 路径 | 作用 |
| --- | --- |
| `CLI.md` | 所有命令、参数、输入输出与错误行为 |
| `SPEC.md` | 清单、递归依赖、归档、锁文件、提示词和技能格式 |
| `ACCEPTANCE.md` | 独立于实现的可观察验收条件 |
| `templates/*.md` | 五个主动作的完整默认模板，作为静态资源原样交付 |
| `skills/*/SKILL.md` | 唯一内置技能 `migrate-to-recipkg`，作为静态资源原样交付 |
| `PHILOSOPHY.md` | 项目目标与“0 代码”的准确范围 |
| `LICENSE.md` | 随资源保留的 MIT 许可 |

## 实现边界

1. 提示词生成是本地字符串替换和资料整理。默认 stdout 只输出提示词；将诊断写到 stderr。`extract` 将目标作为待观察对象写入提示词，不读取或抓取目标软件。
2. `build`、`rewrite`、`add`、`discover` 必须附带根配方及每层依赖的完整 Markdown 材料，不摘要、不丢弃重复作用域的依赖、不静默截断。生成这些提示词时不获取远程资料。
3. 包操作是显式命令。只有 `pack`、`install` 可以为声明的依赖获取远程材料；不执行任何包内容或安装钩子。
4. 验证先于输出或安装。发现缺失依赖、循环、非法文件、危险路径或不匹配校验值时，给出错误而不交付看似完整的结果。
5. `pack` 把递归依赖放入 `.deps/<alias>/`，重写来源为内部相对路径，生成覆盖全包的根 `LOCK.md`。相同输入和来源记录的归档应确定；包可以离开原目录单独使用。
6. 安装以名称和版本区分内容。同一身份的不同内容不得静默覆盖；不通过包内指令启动 Agent。
7. 技能同步使用显式目标目录，只修改已托管且未被用户编辑的文件。保持无关文件与技能；同名不同内容、用户改动和未知已有目录均应明确失败。
8. 不绑定模型厂商或生成软件语言。也不引入模型 API key、托管服务、数据库、后台守护进程或中央包注册表作为基本使用前提。
9. 按 `quality` 依赖检查实现的代码结构、文档可读性与性能声明。性能目标必须来自可观察的场景或明确标为待确认；不得编造基准数字。

## 实现建议

把清单解析、依赖解析、归档验证、提示词渲染、安装仓库与技能同步分成职责清晰的部分。它们之间传递可验证的数据，避免以执行提示词来“解析”配置。

模板只做一次占位符替换。保留来源标识与文件索引，帮助接收提示词的 Agent 理解材料边界。文本中出现类似指令的句子不能改变 CLI 自身的权限或流程。

先完成一个本地三层依赖示例，再验证归档脱离原目录后仍可生成完整提示词。最后验证打包安装后的程序能找到所有静态模板与技能，不能只在源码目录中正常工作。

## 交付要求

- 可运行的 Recipkg CLI、安装或启动方法、所有模板和技能资源。
- 包格式和命令说明，以及离线可用的三层配方演示。
- `ACCEPTANCE.md` 每项的真实验证记录，包含环境、执行方式、结果与未验证项。
- 明确记录与本配方的差异。未经验证不能声称逐字节复刻了参考实现；目标是完整实现这里规定的公开行为。
