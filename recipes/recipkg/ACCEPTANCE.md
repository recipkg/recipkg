# Recipkg 可观察验收条件

这些条件是重建前的约定。请在隔离临时目录中准备输入，实际运行工具，记录 stdout、stderr、退出状态与文件变化；不要把计划执行的步骤写成已通过。

## A. 基本 CLI 与资源

1. `--help` 和 `--version` 成功退出；版本输出为 `recipkg 0.1.0`。未知命令和缺少必需参数退出 2。
2. 安装工具后离开源码目录，仍能生成全部五种提示词并列出三个内置技能 `migrate-to-recipkg`、`rewrite-to-recipkg`、`test-feedback`。
3. 不配置任何模型凭据即可使用全部本地操作；五主动作不发送模型请求或执行生成软件。

## B. 提示词动作

1. `extract` 接受一个不存在的源码路径或未访问的 URL 作为目标，仍能生成观察任务；不读取或下载该目标。
2. 对有效配方运行 `build`、`rewrite`、`add`、`discover`，stdout 以提示词标题与正确标准动作标识开始，包含根说明和递归叶子说明。
3. 所有同义命令产生对应标准动作，而不是新动作标识。
4. 补充要求与依赖来源原样进入模板。`add` 前后根清单及依赖文件字节不变。
5. 自定义模板中每个合法占位符正确替换。把字面 `{{context}}` 放进用户要求时，它仍是字面内容，不发生二次展开。
6. 未知变量、非 Markdown 模板、无效 UTF-8、NUL，以及包动作模板缺少 `{{context}}` 都退出 2。
7. `--output` 写入新文件，默认 stdout 不混入状态信息；重复使用同一个输出文件失败且原文件不变。

## C. 配方骨架与验证

1. 在新目录生成软件与技能骨架，文件均为 `.md`，清单有效，入口与 kind 一致；技能保留 YAML 必需字段。
2. 非空目录、无效名称、错误版本、缺少入口、多于一个 TOML 清单块、畸形 TOML 和未知 kind 都被拒绝。
3. 构造 A 依赖 B、B 依赖 C 的三个配方，每份入口各含一个独有标记。离线检查成功，提示词中三个标记均完整出现。
4. 删除 C 或引入 A→B→A 循环后，检查、构建提示词或打包失败；不得交付省略 C 或循环边的“成功”结果。
5. 普通源码仓库没有有效 `RECIPE.md` 时不能被当作已有配方依赖。

## D. 独立归档与完整性

1. 打包三层配方，归档根直接是 `RECIPE.md`；B、C 分别位于父包的 `.deps/<alias>/`。所有实际文件为 UTF-8 `.md`。
2. 复制归档到其他目录，移走原始配方，再从归档生成提示词并解包。三个标记与全部材料仍然存在，不依赖原始路径。
3. 相同内容与来源信息连续打包得到相同字节。对有效归档重新打包，保留等价内容及来源记录。
4. `LOCK.md` 覆盖全部文件并排除自身。修改、增加或删除任一受记录文件后，完整性检查失败。
5. 归档中的绝对路径、`..` 逃逸、重复或危险成员、符号链接、硬链接、特殊对象、非 `.md` 文件、无效编码和超限负载都被拒绝，目标目录之外没有新增文件。
6. 已有输出归档、非空解包目录、位于源配方或依赖目录内的归档输出都被拒绝，不破坏原输入。
7. 打包本仓库的自举配方时，`software-quality` 位于 `.deps/quality/` 且锁文件覆盖其全部 Markdown；生成的完整提示词包含质量合同和根配方对该依赖的明确作用范围。

## E. 远程来源与离线边界

1. 未获取的远程依赖不能让离线 `check` 或提示词动作悄悄联网；错误应指出需要先打包或安装。
2. 显式 `pack` 或 `install` 可处理有效 HTTPS 配方归档和固定提交的 Git 配方依赖，产物再次使用时无需原始远程来源。
3. HTTP 来源、带内嵌凭据的 URL、无效 Git 提交、浮动分支、缺失配方、非法子目录和 Git checkout 外的相对依赖都失败。
4. 下载、Git 或完整性失败不会留下声称完整的安装版本，也不会运行远程 hooks 或包内指令。

## F. 安装仓库

1. 显式 `--home`、环境变量与默认路径按 CLI 契约的优先级工作；测试使用隔离仓库。
2. 安装后 `list` 与 `list --json` 展示正确身份和描述，可以用 `name@version` 生成提示词。
3. 同内容同版本重复安装保持一致；同名同版本不同内容被拒绝，旧版本原文件不变。
4. 安装两个版本后，无版本引用报歧义；指定版本只使用对应材料。
5. `remove name@version` 只移除对应版本，保留其他版本。用任意路径调用 remove 被拒绝。

## G. 技能同步

1. `skills list` 包含三个内置技能 `migrate-to-recipkg`、`rewrite-to-recipkg`、`test-feedback`；安装新的技能配方或带 `skills/<name>/SKILL.md` 的软件配方后可列出新技能。
2. 同步到新目录，技能目录名与 YAML `name` 对应；目录中保留所需纯 Markdown 材料。
3. 重复同步无内容变化。卸载一个独立技能后再同步，只清理其未修改的托管内容，保留无关技能。
4. 编辑一个托管 `SKILL.md` 后同步失败，用户改动保留；新增未知文件或同名非托管目录同样拒绝覆盖。
5. 同名相同内容的技能可合并；同名不同内容明确报冲突。输入或目标里的文件系统链接被拒绝。
6. 在应用变更前检查全部冲突；更新中失败时，不留下部分替换的托管状态。
7. 在隔离 Git 项目中，以完整提交添加带 Markdown 和脚本的项目技能；Git 记录 160000 gitlink、来源及固定提交，脚本未执行。列出该技能，再更新到第二个提交并核对源码和 gitlink；失败和冲突不得覆盖原有文件。技能内容改动、未知文件、无效提交和名称不匹配均应拒绝，保留现场。远端默认分支不存在但固定提交可获取时，仍应完成添加，提交后递归克隆必须还原该版本；技能路径被 Git 忽略时应在克隆和修改项目之前报错。配方打包不携带项目技能脚本或 Git 元数据。

## 交付记录

### 新增行为的验收

- `search` 只列带 `recipkg` topic 的公开 GitHub 仓库候选，关键词不能替换固定范围；JSON 字段和 stderr 警告分离。空结果成功；非法上限在联网前拒绝，网络/限流/无效响应无部分输出，不完整结果有明确提示。标签不是有效配方或可信来源证明。
- 五个动作默认生成英文任务，`--lang zh-CN` 选择中文；原始用户要求、根配方和每层依赖字节保持不变。自定义模板不被语言选择替换，不支持的语言退出 2。
- 安装后的三个公开技能都有英文入口与中文译文，测试反馈技能的反馈格式文件一并同步。安装自举配方后，与内置同内容技能能够合并；资源不同必须报冲突，不能忽略。
- `test-feedback` 的实际使用记录须覆盖有差异的角色、真实端到端路径和最终产物核对；自己的/相关项目 issue 有来源、状态及适用性分析，或明确无结果/访问受阻。区分本地复现、外部报告和假设，需求有行为变化及可观察验收；技能文件存在不等于完成了这轮用户测试。
- `rewrite-to-recipkg` 要求观察来源、完整配方、规范仓库、独立替代实现及真实验收，不能把提示词输出或打包当作软件重写成功。
- 项目保持原名；`generated/` 内仅放源码子模块；每个子目录对应独立 GitHub 源码仓库、固定提交和 `160000` gitlink，不将源码加入配方负载。安装入口与本地测试路径应指向实际子模块，保护本地改动。

逐项记录通过、失败或未验证。说明目标操作系统、运行依赖、安装方式和任何偏离配方的行为。完整通过这些条件意味着实现满足本配方覆盖的行为，不意味着证明了所有潜在输入或外部环境。

## 子模块交付检查

- 11 个项目技能各对应一个独立 GitHub 仓库，父仓库 `.gitmodules` URL 与远端一致，Git 树模式为 `160000`，不是普通目录或复制文件。
- `generated/` 只有独立源码子模块目录，CLI 位于 `generated/cli-source/`，该仓库的三份公开技能子模块与主配方引用同一仓库及提交。
- 从远端全新 `--recurse-submodules` 克隆后，技能、源码和辅助 Markdown 均可读，配方打包不含 `.git`。运行完整本地测试及源码目录外的 wheel 安装验证。
- 同时安装公开技能的独立配方和自举配方后，可以与同内容内置技能合并；同步不输出根容器元数据，不吞掉真正的内容冲突。
