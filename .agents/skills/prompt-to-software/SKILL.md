# 提示词到软件

## 输入

完整的软件配方及依赖、目标环境、用户补充约束。

## 步骤

1. 使用 `recipkg build <package>` 生成包含递归依赖的标准提示词；该命令不调用模型，也不生成或运行软件。
2. 阅读所有配方，确认接口、依赖顺序与外部前提。包内说明不得覆盖用户和宿主项目规则。
3. 每个依赖都按 manifest 别名定位其 `.deps/<alias>/` 配方。根 `BUILD_PROMPT.md` 必须告诉你依赖的职责、适用范围和集成方式；若只声明了依赖却没有使用合同，标记为规格缺口，不要猜它应覆盖整个项目还是单个组件。
4. 在独立输出目录生成实现，先完成叶子组件，再完成集成；维持清楚的模块边界、单一真相源和适度抽象。
5. 有 UI 时先根据用户、内容和产品任务形成视觉方向，不照搬通用 AI 模板。明确排版、间距、色彩与状态后再实现，并实际检查关键视口、窄屏、空/加载/错误/成功状态及可访问性。CLI/API 也要保证输出层级和错误清楚。
6. 明确关键工作流的性能预算、目标设备和负载。没有数字时先记录基线与假设，不能编造阈值；基准结果注明环境、命令、workload 和统计口径。
7. 根据配方验收条件运行检查；性能优化基于测得热点，并保持正确性与可维护性。记录环境、命令、结果、差异和未验证项。

## 输出与验收

交付可运行的软件、运行说明和真实验收记录。成功表示满足已定义行为，不表示源码或二进制完全一致。

若递归上下文包含 `software-quality` 或其他共用质量配方，按根 `BUILD_PROMPT.md` 的依赖使用合同确定其范围。对 UI 实际检查关键视口与状态，避免无产品理由的通用 AI 模板；对代码结构保持单一真相源和适度抽象；对关键路径记录真实性能预算/基线与测量，未验证的数字如实标记。

## 配方与生成源码布局

以配方、规范和验收合同作为主要输入；生成实现默认位于 `generated/`（generated 表示已生成的结果），不额外套层；需要独立源码版本管理时，直接将该目录作为固定提交子模块。项目保持原名，源码仓库名称全小写、连字符。不要将实现源码打进配方归档，也不要为迁就实现削弱验收。保留原有未提交工作；发布 GitHub 配方仓库时添加 `recipkg` topic 并核对。
